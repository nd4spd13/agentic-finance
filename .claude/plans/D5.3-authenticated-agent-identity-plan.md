# D5.3 — Authenticated agent identity (implementation plan)

Status: **draft / scoping.** Phase reference: `packages/docs/plans/desktop-app.md` Phase D5.
Supersedes the interim "Option 1" bug fix (local stdio server reads passphrase from safeStorage); see §9.

## 1. Goal & acceptance (restated from D5.3)

Replace the **self-asserted, process-pinned** `agent_id` with a **cryptographically authenticated, per-connection** identity. Scope is minted server-side from the agent profile, never taken from a client-supplied claim.

Acceptance (from the roadmap, unchanged):
1. An agent cannot present as another profile by asserting an id.
2. The scope the resource layer enforces binds to an authenticated client key.
3. A copied/replayed token is rejected.
4. Policy lookup keys off the **verified** identity, not `CLAD_AGENT_ID`.

## 2. The core architectural shift (why this is a transport change, not a patch)

Today agent identity is a **process-lifetime constant**:

- Resolved once at startup from env — `packages/mcp-server/src/server.ts:85`
  (`CLAD_AGENT_ID_ARG` > `CLAD_AGENT_ID` > `'default-agent'`).
- Threaded as `deps.agentId` into every `handleToolCall` (`server.ts:118`) → `ToolContext.agentId` (`packages/mcp-server/src/types.ts:3`).
- The policy engine keys off it: `policy.agents[agentId]` — `packages/core/src/policy/evaluator.ts:21,31`.
- The audit log records it — `server.ts:63,67`.

So **one stdio process == one agent, asserted via env**. Anyone who can spawn the process or edit the MCP client config picks any profile. stdio has no channel to carry a credential, so authenticity is impossible on it.

**The shift:** agent identity moves from "process env constant" to "principal derived from a verified credential presented per connection." That requires a transport that can carry a bearer credential + possession proof → **Streamable HTTP transport + OAuth 2.1**. Crucially, everything *downstream* of `agentId` stays the same — the policy engine already keys off `agentId`; we only change **where `agentId` comes from** (a trusted token instead of spoofable env). That containment is what makes this tractable.

## 3. Workstreams

### WS1 — Streamable HTTP transport (alongside stdio)
- Add an HTTP MCP server using the SDK's `StreamableHTTPServerTransport` (verify export name/shape against the installed `@modelcontextprotocol/sdk@^1`). Bind to `127.0.0.1:<port>` only — never `0.0.0.0`.
- Keep the existing `StdioServerTransport` path for the `dummy`/local-dev provider (no-auth, unchanged) so we don't regress the current CLI/Claude-Desktop-config flow while HTTP matures.
- New entry: `packages/mcp-server/src/http-server.ts` (mirrors `server.ts`'s wiring but over HTTP). Factor the shared `handleToolCall` + tool registration so both transports call identical logic.
- Host an HTTP app (Express or `node:http`) that mounts: the MCP endpoint (`POST /mcp`), the OAuth metadata/AS endpoints (WS2), and health.

### WS2 — OAuth 2.1 authorization + resource server
Clad is **both** the resource server and the (local) authorization server — it owns the agent profiles, so there's no external IdP. Use the SDK's `server/auth` helpers where possible (`mcpAuthRouter`, bearer/DPoP middleware — verify against installed SDK), backfilling only what's missing.

Endpoints (RFCs called out by D5.3):
- `GET /.well-known/oauth-protected-resource` — Protected Resource Metadata (RFC 9728), points clients at the AS + declares supported schemes.
- `GET /.well-known/oauth-authorization-server` — AS metadata (RFC 8414).
- `POST /register` — Dynamic Client Registration (RFC 7591); mcp-remote and Claude use DCR.
- `GET /authorize` — **the consent step** (WS4): renders the human approval that binds an OAuth client to an agent profile; issues an auth code (PKCE S256 required).
- `POST /token` — auth-code+PKCE exchange → access token (+ refresh). Token is **opaque** (server-side lookup), not JWT — single-process owner means instant revocation and no signing-key management; revisit if a stateless multi-node story ever appears.
- **Scope minting:** the granted scope is derived **server-side** from `policy.agents[profile]` at authorize time and stored on the grant. The `/token` response never echoes a client-supplied scope claim.

Token binding (acceptance #2/#3): **DPoP (RFC 9449)** — pragmatic pick over mTLS for a local app. Each request carries a DPoP proof JWT signed by a client-held key; the access token is bound to that key's thumbprint. A token copied without the key is rejected. **Binding is per-token, not a global server switch — see §10 for the multi-client posture and why we do NOT mandate DPoP server-wide.**

### WS3 — Resource-layer enforcement: identity from token, not env
- Add auth middleware on `POST /mcp`: validate `Authorization: Bearer` + DPoP proof → resolve token → **verified agent profile id**. Reject (401 + `WWW-Authenticate` pointing at PRM) on any failure.
- Replace the process-constant `agentId` with a **per-request principal**: `handleToolCall` takes `agentId` from the authenticated request context, not `deps.agentId`. `ToolContext.agentId` now originates from the verified token.
- Everything downstream (`evaluator.ts`, audit logging) is **unchanged** — same `policy.agents[agentId]` lookup, now fed a trusted value.
- On the stdio (dummy) path, `agentId` still comes from env — acceptable because that path serves only non-sensitive dummy data. Gate: the HTTP/authenticated path is the *only* one allowed to construct a real (`plaid`/`simplefin`) provider. (Enforce in `provider-factory.ts` or the transport wiring.)

### WS4 — Consent / enrollment + revocation UI (desktop app)
- `/authorize` renders (in a `BrowserWindow` or system browser per the D3.1 precedent) a consent screen: *"Claude Desktop wants to connect as profile «analyst» with scopes: read balances, read transactions (90d lookback), request actions ≤ $X. Approve?"*
- On approve: bind the DCR client → chosen agent profile; issue auth code.
- Connected-clients management: list grants, show last-used (from audit log), **revoke** (acceptance-relevant: revocation must immediately reject the token).
- All secret material stays in the main process; renderer sees display-safe grant metadata only (standing checklist item 1).

### WS5 — Encrypted credential/grant store
- New store for: registered clients, issued grants, refresh tokens, DPoP key thumbprints.
- Reuse the existing AES-256-GCM + safeStorage-held-key pattern (`packages/core/src/security/crypto.ts`, `token-store.ts`) — standing checklist item 6 ("no plaintext at-rest secret material"); `0600` file perms (item 5).
- Likely `packages/core/src/security/grant-store.ts`, sibling to `token-store.ts`.

### WS6 — mcp-remote compatibility (the actual delivery vehicle)
- Claude Desktop reaches a local HTTP server via `npx mcp-remote http://127.0.0.1:<port>/mcp` in its stdio config (established in prior investigation; localhost is rejected by native Custom Connectors, so mcp-remote is the local path). mcp-remote handles browser-open + callback + token cache.
- End-to-end acceptance test: Claude Desktop lists clad tools and fetches **real SimpleFIN** data through the OAuth'd local HTTP server (this is also what finally closes the original "3 dummy accounts" bug — §9).

### WS7 — KYA / TrustProvider seam (coordinate, don't invent)
- No `TrustProvider`/KYA code exists today (grep-confirmed: only the D5.3 doc line references it). Define the seam so identity verification + scope minting route through a `TrustProvider` interface rather than hard-coding, leaving room for the KYA plan to slot in. Keep this an **interface boundary**, not a full KYA build — that's a separate phase.

## 4. Sequencing (walking skeleton first)

1. **M1 — Walking skeleton, no security value yet.** HTTP transport (WS1) serving the existing tools with a **static bearer** placeholder + per-request `agentId` plumbing (WS3). Proves the transport swap and the identity-from-request refactor in isolation.
2. **M2 — Real OAuth, bearer only.** WS2 authorize/token/DCR + WS5 store + WS4 consent. Tokens work; DPoP not yet. mcp-remote connects and fetches real data (WS6). Acceptance #1 and #4 met.
3. **M3 — Sender-constrained.** Add DPoP binding + replay rejection (acceptance #2/#3). Resolve §7.1 first.
4. **M4 — Revocation + hardening + D5.4 threat-model checks.**

Ship M1–M2 behind a dev/beta flag; the stdio+dummy path stays default until M2 proves out.

## 5. Dependencies & ordering vs. the rest of D5
- **D5.2 (field shaping) should land first.** Authenticated identity gates allow/deny + *scoped field visibility*; without D5.2, a verified identity still returns unshaped payloads, so per-agent scope is only half-real. D5.3 is most valuable stacked on D5.2.
- **D5.1 (encrypted cache)** is independent but required for the combined **D5.4** threat model ("no reading around the MCP layer").
- D5.3 is the largest single item in D5 — treat M1–M4 as separately reviewable PRs, not one drop.

## 6. Testing
- Unit: metadata documents (RFC 9728/8414 shape), PKCE validation, scope-minting derives from profile and ignores client-supplied scope, DPoP proof validation + thumbprint binding, replay rejection, revocation → immediate 401.
- Integration: full authorize→token→call happy path over HTTP; unknown/blocked profile denied; token for profile A cannot exercise profile B's scope.
- E2E: mcp-remote + Claude Desktop lists tools and reads real SimpleFIN data (WS6).
- Threat-model note in the S0-spike style for **D5.4** (§ acceptance: spoof attempt, replayed token, out-of-band cache read).

## 7. Open questions / risks
1. **DPoP client support (resolved — see §10).** DPoP is a per-OAuth-client capability, and as of early 2026 it is not in the MCP auth spec and not shipped by mainstream clients (Claude connectors are bearer-only; mcp-remote support unconfirmed). Decision: do **not** mandate DPoP; go bearer-baseline + DPoP-optional-per-token + scope-gated (§10). Residual item for M3: confirm whether the pinned mcp-remote can present a DPoP proof, which only gates whether *sensitive* scopes are reachable locally — not whether clients can connect at all.
2. **Authorization server in-app.** Confirm how much the SDK's `server/auth` provides vs. what we hand-roll (authorize UI, grant store, DCR). Verify exact exports against the installed `@modelcontextprotocol/sdk@^1`.
3. **TrustProvider shape.** Define the minimal interface now without pulling the full KYA plan forward.
4. **Port allocation & discovery.** Fixed vs. ephemeral local port; how mcp-remote's configured URL stays valid across restarts.
5. **Unsigned-build Keychain churn** (desktop-app.md D4.3): safeStorage ciphertext (grant store) can't be decrypted after a differently-signed rebuild — the connected-clients UI must degrade gracefully ("re-connect") exactly like the existing credential path.

## 8. Effort (rough)
Large. M1 small; M2 is the bulk (OAuth AS + consent UI + store); M3 gated on §7.1; M4 moderate. Plan for four+ reviewable PRs across WS1–WS7, not a single change.

## 9. Relationship to the current bug (the Approach A interim fix)
The live "MCP returns 3 dummy accounts" bug is because the MCP-client config never sets `CLAD_PROVIDER` (defaults to `dummy`), and no config path can safely carry the token-store passphrase.

The naive fix — have the spawned server read the sealed passphrase itself — is **not buildable**: the passphrase is unlocked only via Electron `safeStorage` in the desktop main process (`passphrase.ts`/`sealed-file.ts`), and MCP servers are spawned as `ELECTRON_RUN_AS_NODE` plain Node, which has no `safeStorage`. The one process that holds the unlocked passphrase is the already-running desktop app.

**Chosen interim fix — Approach A (loopback HTTP):** the desktop app already spawns a supervised MCP child with the passphrase correctly injected in its env (`mcp-server-env.ts` `buildServerEnv`); give that child a Streamable-HTTP transport bound to `127.0.0.1`, point the manager's readiness check at it over HTTP, and rewrite the "Connect to Claude Desktop" entry to reach it via `mcp-remote`. The passphrase never leaves the child's process; nothing secret touches any config file. It's unauthenticated on the loopback port (acceptable now — same threat surface as the beta's already-plaintext cache; §10 explains why real auth waits). This is the same "unlock via local key custody, not via config" principle D5.3 generalizes across a network boundary, and is literally **WS1 + WS6 of this plan minus OAuth** — foundation, not throwaway. When D5.3 (M2) lands, the OAuth'd path supersedes the unauthenticated loopback.

## 10. Multi-client / DPoP posture (decision)

**Decision: bearer-baseline, DPoP-optional, bound per-token, gated by scope. Never mandate DPoP server-wide.**

Context (verified early 2026): DPoP (RFC 9449) is **not** in the MCP authorization spec (2025-06-18 mandates only OAuth 2.1 + PKCE), and no mainstream MCP client ships it yet — Claude's native connectors send plain `Authorization: Bearer`; mcp-remote support is unconfirmed; most other clients (OpenAI, IDE MCP, custom) are bearer-only. Mandating DPoP today would lock out *every* client, including Claude. So the premise "some clients do DPoP, some don't" is really "almost none do yet" — and server policy, not client choice, is what would cause fragmentation.

How to support heterogeneous clients without a weakest-link hole:
- **Bind per-token, not per-server.** DPoP binding is a property of the issued grant (the `cnf`/`jkt` thumbprint claim). A DPoP-capable client gets a sender-constrained token the resource server enforces a proof for; a bearer-only client gets a plain token. The two coexist.
- **Downgrade-safe.** The resource server MUST refuse to accept a DPoP-bound token as a plain bearer. Mixing clients then never weakens the constrained ones.
- **Degrade gracefully.** A client that doesn't understand the DPoP metadata just uses bearer; the AS advertises `dpop_signing_alg_values_supported` for those that do. The only hard break is *requiring* it.
- **The lever — gate scope on binding, checked at enrollment.** Low-sensitivity read scopes → accept bearer (interop with everything now, Claude included). High-privilege scopes (broad data, anything action-bearing) → require a DPoP-bound token; refuse to mint a bearer token for that agent profile. Client capability thus maps onto *what a profile may do*, decided once at enrollment — a weaker client simply can't be granted the dangerous scopes rather than being rejected outright.

Where the capability physically lives (the "different clients" axis): it's a property of whichever component holds the token and makes the HTTP call — often a proxy/cloud layer, not the chat app. Local loopback (Approach A / WS6) → **mcp-remote**. Native Custom Connector → **Anthropic's cloud infra**. Other AI clients → each itself.

Consequence for acceptance #3 ("a copied/replayed token is rejected"): with the ecosystem bearer-only today, #3 is **not achievable for any client yet** via standard flows — it's aspirational until client DPoP support matures. This is a further reason the loopback fix (Approach A, no tokens at all) is the right "now," and full D5.3 waits on both the KYA/`TrustProvider` design *and* ecosystem DPoP support. Build the resource server bearer-baseline so DPoP lights up client-by-client, with zero server rework, as support lands.
